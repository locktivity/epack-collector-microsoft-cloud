# Changelog

## Unreleased

## v0.2.8

- The collector is built on epack v0.11.2.
- In `idp-posture`, members whose user principal name is in a federated domain sign in through the identity provider the domain is federated with, which decides whether they use MFA. When an enabled member is in one, `user_security.mfa_user_count`, `phishing_resistant_user_count`, `mfa_coverage_pct` and `mfa_phishing_resistant_pct`, and `policy.mfa_required`, `mfa_required_user_count` and `mfa_required_coverage_pct` are left out with an `unsupported` gap that names the domain. When a privileged user is in one, `privileged_access.privileged_mfa_user_count`, `privileged_phishing_resistant_user_count`, `privileged_mfa_coverage_pct` and `privileged_phishing_resistant_pct` are left out the same way. Through v0.2.7 a federated member with no method registered in Entra ID counted as having no MFA. The user list now reads each user's `userPrincipalName`, and the organization's verified domains give which are federated. `entra`'s own `posture` and `policy` values don't change.

## v0.2.7

- `entra`'s MFA registration values are left out with a `vendor_error` gap when Microsoft's registration report lists none of the tenant's enabled members, as for a new tenant. These are `posture.denominator_enabled_member_users`, `mfa_coverage`, `mfa_phishing_resistant`, `mfa_weak_method_only` and `sspr_registered`, and `cloud-posture`'s `iam.mfa_coverage_pct`. Through v0.2.6 the denominator was 0 and the percentages were null with no gap.
- `cloud-posture`'s `iam.root_mfa_enabled` and `root_access_protected` are left out with a `vendor_error` gap when the registration report doesn't list every Global Administrator. Through v0.2.6 a Global Administrator missing from the report counted as not registered for MFA, so both values were false.
- The values that count members are left out with a `not_read` gap when Microsoft Graph gives an enabled user no user type, as it can for older accounts. These are `users.enabled_member_users_count`, the MFA registration values, the MFA policy coverage, and the normalized `user_count`, `inactive_user_count` and `inactive_pct`. `guest_pct` is left out when any user has no type, `privileged_guest_count` when a privileged user has none, and `access-posture`'s `external_member_count` when a member with an Azure role has none. `inactive_guest_pct` is left out when the sign-in activity list gives an enabled user no type. `users_present` and `external_members_present` stay true when other users show there are some. Through v0.2.6 a user with no type counted as neither a member nor a guest.

## v0.2.6

- `artifacts/microsoft-cloud.access-posture.json` has `root` now, in the totals and in each subscription's scope. Azure has no built-in root account, so `root_accounts_present` and `root_access_keys_present` are false and `root_mfa_coverage_pct` is null. From the audit level, `root_account_count` and `root_mfa_account_count` are 0. Before, `root` was left out with an `unsupported` gap. A profile test that applies only when `root.root_accounts_present` is true no longer applies to Azure.

## v0.2.5

- The privileged user values and the Global Administrator count read on real tenants again. Microsoft Graph v1.0 returns `isPrivileged` as null on every role definition, though it filters on it, so v0.2.4 found every role unclassified: the values over privileged users were left out with a `not_read` gap, and `super_admin_count` read 0. The collector now reads the role definitions once filtered on `isPrivileged eq true` and once on `isPrivileged eq false`, and counts Global Administrator as privileged whatever the classification says.
- `vault_soft_delete_pct` and `vault_immutability_pct` in `azure` read each Recovery Services vault on its own, with the Reader role the collector already holds, since Azure's vault list leaves out a vault's security settings. Through v0.2.4 a vault listed without them counted as having soft delete and immutability off. A vault that can't be read, or whose read gives no soft delete state, leaves both values out with a gap.

## v0.2.4

- The collector is built on epack v0.10.6 and Go 1.26.11.
- `storage.encryption_pct` and `encrypted_storage_resource_count` in `artifacts/microsoft-cloud.cloud-posture.json` count every storage account encrypted at rest, with Azure's own key or a customer-managed one. Azure encrypts every storage account at rest, so the value is 100 for a subscription whose accounts report a key source. Through v0.2.3 they counted customer-managed keys only, which `encryption_cmk_pct` in `artifacts/microsoft-cloud.azure.json` still reports.
- The cloud-posture storage block has `network_restricted_pct` and `network_restricted_storage_resource_count`: the storage accounts with public network access turned off, or whose network rules deny by default, so only listed networks and private endpoints can connect. `public_access_blocked_pct` still counts anonymous blob access only.
- `artifacts/microsoft-cloud.idp-posture.json` has `privileged_access.standing_privileged_users_count` and `standing_privileged_users_present`: the privileged users who hold a privileged role at all times. A user whose every privileged role is one their PIM eligibility lists has activated it just in time and doesn't count. Through v0.2.3 the collector left both out, so controls that read them were never evaluated on Microsoft packs.
- At the audit level, `user_security.mfa_user_count` and `phishing_resistant_user_count` give the counts behind the MFA percentages, when Microsoft's registration report lists every enabled member. When it lists only some, they are left out with a `vendor_error` gap and the percentages stay, taken over the members it lists.
- In `entra` and `idp-posture`, Conditional Access policies combine. `policy.mfa_required` is true when the enabled policies that include all users, between them, require MFA for or block every sign-in to every app, whatever its client, device platform, location, sign-in risk, user risk, insider risk and authentication flow. A policy for one app and another for every other app are enough, and so are two policies for trusted and untrusted locations, or an MFA policy for browsers and mobile and desktop apps beside one that blocks legacy authentication. A list of every known platform doesn't cover a platform Microsoft doesn't recognize, which only all does. Through v0.2.3 one policy had to cover everything, but a policy for one app, or for browser sign-ins alone, also counted.
- The MFA policy coverage counts the enabled members whose every sign-in the policies, between them, require MFA for or block. A user a policy excludes by ID is left out of it, whether the policy includes all users or lists them. `legacy_auth_blocked` combines the policies that block legacy clients the same way.
- What the collector can't evaluate no longer turns into true or false. A device filter, an app filter, a named location whose trust can't be read, and a condition, value or grant control the collector doesn't recognize, such as one Microsoft adds later, are each taken both ways, as group and role membership already were. When the answer differs, `mfa_required`, `legacy_auth_blocked` or the coverage is left out with a `not_read` gap that names the cause. The check splits sign-ins only where policies differ, so a tenant with 100,000 users and hundreds of policies takes well under a second, and one whose policies would need more kinds of sign-in checked than the collector allows gets the same gap rather than a run that doesn't finish. The collector reads `/identity/conditionalAccess/namedLocations`, with the Policy.Read.All it already holds, when a policy names a location.
- `entra`'s `all_cloud_apps_mfa_required` no longer counts a policy that excludes an app or has an app filter. It and `admin_portals_mfa_required` count a policy for browsers and mobile and desktop apps only when legacy authentication is blocked.
- With security defaults on, the MFA policy coverage counts the enabled members who hold an admin role security defaults name, such as Global Administrator, since security defaults require MFA of other users only when Microsoft judges a sign-in risky. Through v0.2.3 it counted every enabled member. `mfa_required` stays false under security defaults, and `legacy_auth_blocked` is true, since they block legacy authentication for everyone. Both hold without a Conditional Access license and when the policies can't be read, since no policy can be enabled beside security defaults. With no enabled policy and security defaults unread, `legacy_auth_blocked` is left out with a gap.
- Privileged users are those who hold a directory role Microsoft marks privileged, apart from roles whose every directory action only reads, such as Global Reader. The collector reads the role definitions from `/roleManagement/directory/roleDefinitions`, with the RoleManagement.Read.Directory it already holds, so Microsoft's own classification decides, and a custom role with sensitive permissions counts too. A user who holds only a role Microsoft hasn't classified leaves the privileged values out with a gap. Through v0.2.3 the collector counted a fixed list of 11 roles, which left out Helpdesk Administrator, Password Administrator, Intune Administrator, every custom role and others Microsoft marks privileged, and counted Exchange Administrator and SharePoint Administrator, which it doesn't. The privileged user values in `entra` and `idp-posture` and the PIM values change for a tenant whose users hold those roles.
- `privileged_access.privileged_users_present` in `idp-posture` is true when a user holds a privileged role directly, even when a group holds one too. Through v0.2.3 it was left out with a `not_read` gap whenever a group held a privileged role. `standing_privileged_users_present` works the same way.
- The privileged MFA percentages are left out with a `vendor_error` gap when Microsoft's registration report doesn't list every privileged user yet. Through v0.2.3 a privileged user missing from the report counted as having no MFA.
- `idp-posture`'s `user_security.inactive_pct` is taken over the enabled members, guests left out, as `user_count` is, and the audit level writes `inactive_user_count` beside it. A member missing from the sign-in activity list counts as inactive. Through v0.2.3 it was taken over every enabled user, guests included. `entra`'s `users.inactive_pct` still includes guests.
- In `access-posture`, an Azure role held anywhere in a subscription makes a member, or for a service principal a credential, including one on a resource group or a resource. Admins are the members with Owner, Contributor, User Access Administrator or Role Based Access Control Administrator over the whole subscription, held on it or above it. Through v0.2.3 the collector read only the role assignments on the subscription and above it, and admins were Owner and User Access Administrator. The role assignment list is now read without the `atScope()` filter, and `azure`'s `rbac.owner_count` still counts Owner on the subscription and above only.
- `ssh_open_to_world_pct` and `rdp_open_to_world_pct` in `azure`, and the matching counts in `cloud-posture`, apply each network security group's rules in priority order, as Azure does. A Deny rule from any address that comes before the Allow rule closes the port. Through v0.2.3 any Allow rule from any address counted, whatever came before it.
- A Microsoft Graph or Azure Resource Manager list whose next page link points to a page already read fails, and the values taken from it are left out with a gap. Through v0.2.3 the collector kept reading the same pages.

## v0.2.3

- The collector is built on epack v0.10.5.
- A trust run no longer writes the tenant or subscription IDs. `tenant_id` in `entra` and `accounts[*].account_id` in `azure` are written from the audit level, so at trust a subscription the collector can't read has an empty entry. At trust, `subscription_errors` and the warnings name a subscription by its place in `subscription_ids`, such as `subscription 2`, and a subscription error gives only the HTTP status and Azure's error code. The audit and internal levels write what they did before.
- The collector result lists the run's targets: the tenant and the configured subscriptions. The tenant is the Entra artifact as a whole, named by its ID and labelled with its default domain, so a trust run, which doesn't write the tenant ID, still shows the domain. A trust run gives no counts.

## v0.2.2

- The collector is built on epack v0.10.2.
- The deprecated `accounts[*].iam` block is left out when `collect` leaves out `access-posture`, with a `not_shared` gap, and the gaps inside it are dropped. v0.2.1 wrote it whatever `collect` listed.

## v0.2.1

- The collector is built on epack v0.10.1.
- `artifacts/microsoft-cloud.cloud-posture.json` has `accounts[*].iam` again, as a deprecated block that epack v0.10.1 declares. Each subscription's entry holds the tenant's values, as in v0.1. A later minor removes the block.
- `iam.mfa_coverage_pct` is a copy of Entra's `posture.mfa_coverage`. `iam.root_mfa_enabled` and `root_access_protected` are both whether every enabled Global Administrator is registered for MFA. They are left out with a gap when the registration report can't be read or the Global Administrator role is assigned to a group.

## v0.2.0

- The collector is built on epack v0.10.0. Its artifact paths stay the same
- Each run writes `artifacts/microsoft-cloud.access-posture.json`, in the `evidencepack/access-posture@v1` format, and `collect` lists it as `access-posture`. It holds counts of the users and service principals with an Azure role assignment on the configured subscriptions. From the audit level, `scopes` has one entry for each subscription.
- `artifacts/microsoft-cloud.cloud-posture.json` no longer has `accounts[*].iam`, since `evidencepack/cloud-posture@v1` no longer has it. The tenant's member users and their MFA registration are still in `idp-posture`, as `user_security.users_present`, `user_count`, and `mfa_coverage_pct`. MFA for privileged roles, Global Administrator included, is in `idp-posture`'s `privileged_access`.
- `iam.root_mfa_enabled` and `iam.root_access_protected` have no new field. Azure has no root account, so `root` is left out of the access file with an `unsupported` gap.
- In the access file, members are the enabled users in the tenant's user list who hold a role. A guest counts as an external member. A member is inactive after 90 days without a successful sign-in. Admins are the members with the Owner or User Access Administrator role.
- Everyone signs in to Azure through Microsoft Entra ID, so the access file's `sign_in.sso_configured` and `sso_required` are true in every subscription. No one can sign in to Azure without Entra ID, so its local member and admin values are false, 0, or null. `sign_in.mfa_required` and `sign_in.scim_enabled` are left out with an `unsupported` gap.
- The access file leaves out `connected_apps` with a `not_read` gap. Microsoft Graph lists the apps with delegated access to Azure Resource Manager in its delegated permission grants, which the collector does not read.
- The access file's credentials are the service principals that hold a role. One counts as never expiring when an active client secret or certificate has no end date or ends more than 50 years after the run. It is overdue for rotation when an active client secret or certificate became valid more than 90 days before the run. The credentials checked are its own and those of the application with its appId. An enabled service principal with any role but a built-in read-only one counts as having write access. When the service principal list can't be read, the write access values are left out with a gap.
- The access file's unused credential values are left out with a `not_read` gap, since Microsoft Graph reports service principal sign-ins only in its beta API. The unrestricted values are 0 when every service principal holds only built-in read-only roles. Otherwise they are left out with a `not_read` gap, since custom role definitions and Conditional Access location conditions are not read.
- When a role is assigned to a group, the access file's counts and percentages over everyone with a role are left out with a `not_read` gap. Group members are not read. The same happens when a role is assigned to an agent identity or a device, since those aren't counted as members or service principals.
- In `entra` and `idp-posture`, the values over privileged users are left out with a `not_read` gap when a privileged directory role is assigned to a group. MFA policy coverage is left out the same way when an MFA policy includes or excludes a group or a role. Values Microsoft never reports, such as locked-out users and password strength, have an `unsupported` gap.
- In `entra` and `idp-posture`, `policy.mfa_required` and the MFA policy coverage count only Conditional Access policies that apply to every sign-in. A policy with a risk level, location, device platform, device filter or authentication flow condition no longer counts. A policy for registering security information doesn't count either. `entra`'s `admin_portals_mfa_required` and `all_cloud_apps_mfa_required` also count only those policies.
- `policy.legacy_auth_blocked` is true only for a block policy that excludes no app. The policy also can't have a risk level, location, device platform, device filter or authentication flow condition.
- `backup.retention_days_min` in `azure` and `cloud-posture` comes from the backup policies that protected items use. A vault's unused DefaultPolicy no longer lowers it. When the protected items can't be read, it is left out with a gap.
- A `permission_denied` gap names the permission to grant. For a Microsoft Graph call it is the application permission, such as `Application.Read.All`. For an Azure Resource Manager call it is the `Reader` role.
- The access file needs no new permission or API call. It is built from the subscriptions' role assignments and the tenant's user, sign-in activity, service principal, and application lists. Each run already reads these. The service principal and application lists now select `appId`, which `Application.Read.All` covers.
